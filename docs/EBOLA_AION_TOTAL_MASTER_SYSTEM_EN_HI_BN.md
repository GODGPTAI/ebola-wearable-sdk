```
   → glasses voice reply + dashboard confirmation
```

### Real developer interaction contract / डेवलपर कैसे जोड़ें

**Do not treat conceptual intent names above as callable SDK methods.** Implement an authenticated intent router in the existing KRISHNA backend, connect to previously approved department handlers and use the existing `/relay/gptgpt6/ask_ai.php` as the orchestrator only after inspecting its actual request schema.

```
{
  "intent": "createOrder",
  "source": "ebola_glasses",
  "account_session": "SERVER_VALIDATED_SESSION",
  "merchant_id": "AUTHORIZED_MERCHANT_REFERENCE",
  "arguments": {"cart_reference": "CART_REFERENCE"},
  "request_approval": true
}
```

**Example above is an API design illustration, not a production endpoint or a client-trusted auth payload.** Server must derive user identity from a verified token/session, validate merchant ownership and all monetary values independently, and return an auditable result.

### Developer implementation gates / डेवलपर के 10 अनिवार्य चरण

1. Reuse account identity and original sponsor link; do not create second signup or QR.
2. Confirm exact PHP route and request schema before wiring.
3. Bind the glasses licence to one device using the tested backend.
4. Register only OEM-supported read-only scan/connection capabilities until hardware passes.
5. Resolve intent to existing director/manager/agent registries rather than invent parallel agents.
6. Validate per-merchant OAuth and scopes for WhatsApp, Google and Meta.
7. Obtain purpose-specific approvals for payments, broadcasting, trade submissions, posting and bookings.
8. Store user media and durable outputs exclusively via existing encrypted Secure Vault.
9. Capture trace, cost, provider response and verified success/failure in audit logs.
10. Test with a real merchant and device, then publish capability-level support labels.

## 39.5 Safety, privacy, Topstep compliance and finance

1. **No unconfirmed voice orders**: require explicit separate confirmation for every consequential order (unless a separately approved narrowly bounded policy exists). Verify STT numbers/sides; reject low-confidence transcription, noisy environments and stale commands.
2. Respect **Topstep's current official rules, platform/API availability and data entitlements**. A website button or AI plan alone does not grant trading API access. Check policies live before offering automation, prop account copy trading, multiple accounts or algorithmic trading.
3. Hard server-side limits: maximum contracts/order, daily loss, drawdown, position limits, session/calendar/market hours, duplicate-order protection, kill switch, stop policy, stale quote, slippage and data provider outage.
4. Final **order/fill truth comes from the broker**, not JA21 or AI response. Show statuses as DRAFT, AWAITING_CONFIRMATION, SUBMITTED, ACCEPTED, PARTIALLY_FILLED, FILLED, REJECTED, CANCEL_REQUESTED, CANCELLED, UNKNOWN; reconcile unknown outcomes before retrying.
5. Protect credentials via existing Secure Vault and short-lived scopes; store minimal sensitive account information. Maintain audit trail (who approved, device, consent, 5-min bar, quote timestamp, costs and official receipt).
6. Bill and report **input tokens, output tokens, realtime vision/voice fees, market data charges and order API fees** separately; never treat “free AI tokens” as free exchange market data or trading rights.
7. Glasses camera and chart analysis are assistive: no guaranteed trade returns, safety or instant execution. Degraded camera feed falls back to authenticated server market data, not invented live readings.
8. Existing 6 Directors and 30 Managers assign jobs through the **actual registry**. Do not add separate phantom JA agents or overwrite the current JA01–JA21 / A18/A28/Phase18/A20/A4/A32 definitions. Preserve their canonical original implementation IDs and evidence.
